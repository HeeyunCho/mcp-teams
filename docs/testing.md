# Testing

Every change starts with a failing test. The fix makes it pass; a refactor keeps it passing.

## Layers

| Folder | What it checks | Runs against | Command |
|---|---|---|---|
| `test/unit/` | Pure functions: Teams parsers and request helpers (`extension/teams.js`), client registration (`src/clients.ts`), a failed call's session note (`failedCallNote`, `isMissingSession` in `src/sessionNote.ts`, #103), the version bump (`scripts/bump-version.mjs`, on a temporary copy of the version files), the build info (`src/buildInfo.ts`, and `scripts/write-build-info.mjs` on a temporary copy of a build: its build id covers `dist/**/*.js` and `extension/` except `pairing.json`, and is checked against a fixed id so that Linux and Windows agree), the repo's line endings (`.gitattributes` gives LF on every OS, checked with `git check-attr` and the global attributes file emptied), the release steps of `version.yml` (run from the YAML on temporary git repositories, `test/helpers/gitRepo.ts`), the tests' timing helpers (`test/helpers/timing.ts`), the native host's registration (`src/nativehost.ts`, on a temporary home) | Nothing external, except temporary folders and git repositories; `reg` is a recording function, never the real registry | `npm run test:unit` |
| `test/integration/` | The extension's service worker (`extension/background.js`), the bridge (`src/bridge.ts`), pairing and the extension folder | A fake `chrome` (`test/helpers/fakeChrome.ts`); real sockets with hubs, peers and a fake extension (`test/helpers/bridgeHarness.ts`) | `npm run test:integration` |
| `test/system/` | The built server (`dist/`) over stdio, as an MCP client sees it | A fake extension on the bridge | `npm run test:system` |

`npm test` runs the build, a typecheck of the tests (`tsconfig.test.json`) and all three layers. It's what CI and the release workflow run. Nothing here talks to Teams; `npm run probe` does, by hand. `npm run measure-memory` is also run by hand (see Memory below).

## Writing a test

- **Pick the lowest layer that shows the problem.** A parser bug is a unit test. "Too many Teams requests" is a worker test that counts requests (`fake.count("chatsvc", /\/messages/)`). "Fails when a session closes" is a bridge test.
- **Worker:** `createFakeChrome({ services })` answers each service (`chatsvc`, `csa`, `mt`, `substrate`, `sharepoint`) per request (`{ service, method, path, url, body }`). Return a JSON body, `reply(status, body, { headers })` for errors (with response headers such as `retry-after`), a promise for a slow answer, or `never()` for a Teams that never answers; a service left out answers 404. The worker's `pageFetch` runs from its source, as Chrome runs it in the page, so its own deadline counts. `fake.freezeTab(id)` makes a tab run no scripts (frozen or asleep) until `fake.wake(id)`; `fake.closeTab(id)` also fails a script running there. `worker.dispatch({ type: "request", id, method, params, timeoutMs, deadline })` runs a request as the bridge sends it (`deadline`: when the server stops waiting, ms since 1970); `{ type: "cancel", id }` withdraws it. `requestWithTurn(worker, id, method, params)` sends it as a hub that hands out turns (#35): its `atGate` resolves once the request waits at a throttle gate, so a test can make something land during that wait, and `response` is its answer. Under a fake clock (`vi.useFakeTimers({ toFake: ["Date"] })`) the clock stands still, so a gate a 429 shut stays shut until the test moves the clock; wait with `until()` then, since `vi.waitFor` moves a fake clock on as it polls. `loadWorker(fake)` loads a fresh copy of the worker (empty caches) and returns its `handlers`, `dispatch` and `registerListeners`. Outside Chrome the worker neither listens nor connects; call `worker.registerListeners()` for tests of `fake.fire(...)` (webRequest), `fake.pageMessage(...)` (confirm and popup pages) or `fake.closeWindow(id)`. `captured: []` starts without Teams sessions; `teamsTab: false` without a Teams tab. Teams' tokens are captured from `fake.fire("beforeSendHeaders", { url, requestHeaders })`, which counts only with a Teams `initiator` (the fake gives one by default; pass another origin, or `initiator: undefined`, for a request from outside the Teams page, #122); make them with `fakeJwt(claims)` (`test/helpers/jwt.ts`), giving `oid` (whose session it is) and, where a token's age matters (an old token of the previous account, #77), `iat` (seconds since 1970). A worker restart: `fake.stopWorker()` drops the worker's listeners (as Chrome does, `chrome.storage` stays), then `loadWorker(fake)` and `registerListeners()` start the next one. A test file that connects a worker over a real socket (`connectWorker`, or `NativeWebSocket`) calls `stopWorkers()` in `afterEach`, after `link.disconnect()` and before the hub's connections end or `vi.unstubAllGlobals()` runs: otherwise the worker's reconnect timer runs `connect()` after the test, without its fake `chrome` (#99). A worker on `InertWebSocket` never closes, so it leaves no retry. Other worker tests need no teardown for the Teams tab's last calls (#103) or the api_traffic log: every Teams-origin request leaves a save of the last calls pending for half a second, and every change to the api_traffic log (a request recorded while it records, or `api_traffic({ clear: true })` emptying a log that isn't empty) one of the log, but each goes to the `chrome.storage.session` it was made under, not to whatever `chrome` is (or isn't) by then. To assert on that storage, call `worker.savePendingCalls()` or `worker.savePendingTraffic()` first rather than waiting.
- **Bridge:** `bridgeHarness()` starts its first `h.session()` on port 0 and keeps the port it got (`h.port`, once a session listens); later sessions join it as peers. A test whose own scripted hub must hold the port first listens on port 0 and passes it: `bridgeHarness(options, { port })`. `h.session()` starts a server's bridge (the first is the hub, later ones peers), and `h.extension({ handle, latencyMs, silent, pong })` connects a scripted fake browser that pairs with a proof. Call `h.cleanup()` in `afterEach`. The `FAST` timings make retries, joins, step-downs and pings take milliseconds; use real timers, not fake ones, and wait with `until(cond, timeoutMs, what)` (`test/helpers/timing.ts`), which polls and names what it waited for when it times out. A test that moves big payloads keeps the real 20 s keep-alive, or a pong queued behind the data gets the connection dropped. A single bridge can take port 0 and report `bridge.port`. A send (`requestSend`) goes only to an extension of 0.2.13 or newer (#22), so a test that sends gives the fake `version: "0.2.13"`; the fake defaults to `0.0.0`, and the worker under the fake `chrome` reports `extension/manifest.json`'s version.
- **Heartbeats (2.3):** `keepAliveMs` is also the hub's heartbeat to peers (a peer drops a hub silent for 2 periods, never under 2 s) and to the worker (it reconnects after 2.25 periods, never under 2 s). `test/integration/heartbeat.test.ts` has a frozen hub (pairs, then never pings) and a raw peer (`pong: false` for a frozen session; `ws._socket.pause()` for one that stops reading); `watchdog.test.ts` has a scripted hub that declares a period and pings or not. Assert *when* a drop happened against the period, measured from the event (the welcome, the backlog showing), and make a race land on purpose (e.g. answer only once the hub has pinged) rather than with a fixed delay. A liveness check (a hub tick, a peer's watchdog) that runs more than half its own wait late (a tick: half a period; the watchdog: half of its 2 periods, at least 1 s; the process stalled) skips its verdict, since the ping or pong may wait unread, but at most once in a row: the next late check judges. `stall(ms)` (`test/helpers/timing.ts`) blocks the test process (hub and peer alike) to show both. The extension's watchdog follows the same rule (half of its own wait: 2.25 periods, at least 2 s), shown the same way in `watchdog.test.ts`.
- **Native host (#123):** `test/integration/hubSocket.test.ts` runs the bridge in-process as the native host (`hostSocket`) on a hub socket of its own (a Unix socket in a temporary folder, or a named pipe named after it on Windows), with the extension's native port attached over in-memory pipes. `test/system/nativeHost.test.ts` runs `dist/hub.js` through `nativeHarness()` (`test/helpers/nativeHost.ts`): a temporary `TEAMS_MCP_HOME` with `"nativeHost": true` and port 0, `h.host(opts)` starts a host with a fake extension speaking Chrome's 4-byte framing on its stdio (it joins chunks), `h.server()` a server that looks for the host, and `h.hostPort()` reads the TCP port the host got from `hub.log`. `TEAMS_MCP_HUB_SOCKET`, `TEAMS_MCP_HUB_LINGER_MS`, `TEAMS_MCP_HUB_KEEPALIVE_MS` and `TEAMS_MCP_HUB_AUTH_TIMEOUT_MS` move the socket and shorten the linger, the pings and the time a connection (or, for a relaying host, the hub socket's holder) has to prove itself; each takes a whole number of ms above 0 written as plain digits (capped at 2^31-1), and any other value (`1e3`, `0x10`, `600.0`) is ignored, so the default applies (`msFromEnv` in `src/native.ts`). A system test that needs only a short `TEAMS_MCP_HUB_AUTH_TIMEOUT_MS` also passes `TEAMS_MCP_HUB_KEEPALIVE_MS` = `DEFAULT_BRIDGE_OPTIONS.keepAliveMs`: at the harness's 200 ms pings, a session or relaying host busy for two of them on a loaded machine is dropped, and its call fails (#145). The extension's side: `createFakeChrome({ nativeHost })` (`test/helpers/fakeChrome.ts`) gives the worker `chrome.runtime.connectNative`, and hands each port it opens to `nativeHost` as a `FakeNativeHost` (`received`, `onPost`, `onClose`, `send(msg)`, `disconnect(error)`, which sets `chrome.runtime.lastError` as Chrome does; `fake.nativePorts` lists them, `fake.connectNative` counts the calls). Without the option there is no `connectNative`, as without the nativeMessaging permission. Like Chrome, the port passes messages later and in order, and its `postMessage` throws on a message over 64 MiB. The worker tries native only when `pairing.json` says `"nativeHost": true`, so a test stubs `fetch` for `chrome-extension://fake-extension-id/pairing.json`. `test/integration/workerNative.test.ts` drives the worker against scripted hosts and a scripted TCP hub (native first, the TCP fallback, 4403, chunks, the size cap); `test/system/extensionNative.test.ts` joins the real worker to the real `dist/hub.js` with `chromeNativeHost(home, socket)` (`test/helpers/nativeHost.ts`), whose `attach` is the `nativeHost` option: each port starts a host process, served directly or relaying. Registration (`src/nativehost.ts`): `test/unit/nativehost.test.ts` runs `installNativeHost`, `registeredHosts` and `batPath` for every OS on a temporary home, with `platform`, `env` (the folders a `.bat` names), `reg` (records the `reg add` arguments) and `regQuery` (reads them back; the real one is `readRegDefault`, which parses a UTF-16LE `reg export` file, since `reg query` prints in the console's code page) passed in, so nothing touches the real registry or home, except one Windows-only test of `readRegDefault` on its own `HKCU\Software\mcp-teams-test-<random>` key, deleted after; a Node or `dist/hub.js` that "moved" is a file in the temporary home that the test deletes. Checks that a path read back from a `.bat` exists run only on a Windows host, where a backslashed path names a file. It also reads the real `extension/manifest.json` for the `nativeMessaging` permission, which `fakeChrome` doesn't need. `test/setupNativeHost.test.ts` runs `setup()` with `"nativeHost"` on and off (HOME, USERPROFILE and LOCALAPPDATA stubbed to a temporary folder, `execFileSync` doubled, so `reg.exe` never runs; `setup(…, { nativeHost: { hubScript } })` points it at a temporary `dist/hub.js`), and `test/integration/nativeHostVersion.test.ts` checks `get_version`'s `nativeHost` field through `registerTools(…, { nativeHost: { home, platform } })`. `test/system/oldHubHandover.test.ts` installs the published `mcp-teams@0.3.52` from npm into a temporary folder and skips when offline (`npmVerdict` in `test/helpers/offline.ts`), except in CI (`CI` set), where it fails instead.
- **server.log (#143):** every server's diagnostic log (`src/serverLog.ts`) is `server.log` in `TEAMS_MCP_HOME`, so a test that starts `dist/index.js` with a temporary `TEAMS_MCP_HOME` never writes to the user's `~/.mcp-teams`. `diagnosticLog({ file, version, role, slowToolMs, slowStatusMs })` points it at any file (`slowStatusMs`, default 2 500: a status read slower than this is logged as `slow=yes`; #153). `teamsStatus(status, { ms, error, aborted })` takes how a read went: a failure's `kind` comes from a fixed set, never from its message text. `watchState()` reads the Teams state as the hub every `TEAMS_MCP_WATCH_MS` (default 60 000; same rules as the other `_MS` variables) through `bridge.backgroundStatus()` with a 15 s limit (#153; its test fakes the timers rather than waiting), which never moves calls to another browser. `test/unit/serverLog.test.ts` checks its lines, its on-change logging and that a message body, token or chat id fed in anywhere never appears; `test/integration/diagnose.test.ts` the bridge's events (`BridgeOptions.diagnose`) and get_version's timed status read; `test/system/serverLog.test.ts` ten processes appending across a rotation, and a real server's start, extension connect and close, failed call and exit.
- **[Hub health] reports:** collect `~/.mcp-teams/server.log` and `server.log.1` first (see the README, "What happened while nobody looked"), then `hub.log` when the native host is on, then `get_version`.
- **Ports:** never fixed, and never picked and then freed (another test file or worktree could take it before it is bound again, #23). Listen on port 0 and read the port from the server that keeps listening (`bridge.port`, `wss.address().port`); a server started from `dist/` with port 0 in its config reports its port in `get_version`.
- **Tool contract:** `test/system/__snapshots__/tools.json` holds every tool's description and input schema. When a change to what the AI sees is intended, update it with `npx vitest run test/system -u` and review the diff.
- **Fixtures:** only fictional people, companies and ids (Alex Doe, Sam Roe, contoso.example, `00000000-…` GUIDs). Never real names, tenants or tokens.

## Memory

`npm run measure-memory` builds and runs `scripts/measure-memory.mjs`: it measures memory instead of guessing it. Per scenario it starts three fresh processes, so the numbers don't mix: the hub, a peer that runs the real tools through an in-memory MCP client, and a fake extension that answers with fictional data shaped like the real extension's. Each samples `heapUsed` every 2 ms and reports it with its peak RSS (the OS's maxRSS). The scenarios: `transcript` reads a long meeting transcript to the end by `continueFrom`, and `history` pages a 5,000-message chat back to the first message by `olderCursor`. The run uses a free port, a pairing token made for it and a temporary `TEAMS_MCP_HOME`, so it never touches `~/.mcp-teams` or the configured port. Sizes: `npm run measure-memory -- --lines 20000 --chunk 40000 --messages 5000 --page 50` (the defaults). It's not part of CI; `test/system/measureMemory.test.ts` only checks that it runs, with small sizes.

**A PR that claims a memory change** puts a before/after table in its description: run the script on the base branch and on the PR's branch (same machine, same Node, same sizes) and paste both, e.g.

| scenario | process | peak RSS (MB) before | after | peak heapUsed (MB) before | after |
|---|---|---:|---:|---:|---:|
| transcript | hub | 51.1 | | 8.8 | |
| transcript | peer | 73.8 | | 21.6 | |
| transcript | extension | 66.6 | | 18.7 | |
| history | hub | 50.6 | | 8.6 | |
| history | peer | 74.5 | | 20.8 | |
| history | extension | 68.4 | | 18.6 | |

(The "before" column is a run of v0.2.14 plus Phase 3 so far, Node 24, macOS.) Peaks vary by a megabyte or two between runs; run each side two or three times and quote the middle one.
