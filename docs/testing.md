# Testing

Every change starts with a failing test. The fix makes it pass; a refactor keeps it passing.

## Layers

| Folder | What it checks | Runs against | Command |
|---|---|---|---|
| `test/unit/` | Pure functions: Teams parsers and request helpers (`extension/teams.js`), client registration (`src/clients.ts`), the version bump (`scripts/bump-version.mjs`, on a temporary copy of the version files) | Nothing external | `npm run test:unit` |
| `test/integration/` | The extension's service worker (`extension/background.js`), the bridge (`src/bridge.ts`), pairing and the extension folder | A fake `chrome` (`test/helpers/fakeChrome.ts`); real sockets with hubs, peers and a fake extension (`test/helpers/bridgeHarness.ts`) | `npm run test:integration` |
| `test/system/` | The built server (`dist/`) over stdio, as an MCP client sees it | A fake extension on the bridge | `npm run test:system` |

`npm test` runs the build, a typecheck of the tests (`tsconfig.test.json`) and all three layers. It's what CI and the release workflow run. Nothing here talks to Teams; `npm run probe` does, by hand.

## Writing a test

- **Pick the lowest layer that shows the problem.** A parser bug is a unit test. "Too many Teams requests" is a worker test that counts requests (`fake.count("chatsvc", /\/messages/)`). "Fails when a session closes" is a bridge test.
- **Worker:** `createFakeChrome({ services })` answers each service (`chatsvc`, `csa`, `mt`, `substrate`, `sharepoint`) per request (`{ service, method, path, url, body }`). Return a JSON body, `reply(status, body, { headers })` for errors (with response headers such as `retry-after`), a promise for a slow answer, or `never()` for a Teams that never answers; a service left out answers 404. The worker's `pageFetch` runs from its source, as Chrome runs it in the page, so its own deadline counts. `fake.freezeTab(id)` makes a tab run no scripts (frozen or asleep) until `fake.wake(id)`; `fake.closeTab(id)` also fails a script running there. `worker.dispatch({ type: "request", id, method, params, timeoutMs, deadline })` runs a request as the bridge sends it (`deadline`: when the server stops waiting, ms since 1970); `{ type: "cancel", id }` withdraws it. `loadWorker(fake)` loads a fresh copy of the worker (empty caches) and returns its `handlers`, `dispatch` and `registerListeners`. Outside Chrome the worker neither listens nor connects; call `worker.registerListeners()` for tests of `fake.fire(...)` (webRequest), `fake.pageMessage(...)` (confirm and popup pages) or `fake.closeWindow(id)`. `captured: []` starts without Teams sessions; `teamsTab: false` without a Teams tab.
- **Bridge:** `bridgeHarness()` starts its first `h.session()` on port 0 and keeps the port it got (`h.port`, once a session listens); later sessions join it as peers. A test whose own scripted hub must hold the port first listens on port 0 and passes it: `bridgeHarness(options, { port })`. `h.session()` starts a server's bridge (the first is the hub, later ones peers), and `h.extension({ handle, latencyMs, silent, pong })` connects a scripted fake browser that pairs with a proof. Call `h.cleanup()` in `afterEach`. The `FAST` timings make retries, joins, step-downs and pings take milliseconds; use real timers, not fake ones. A test that moves big payloads keeps the real 20 s keep-alive, or a pong queued behind the data gets the connection dropped. A single bridge can take port 0 and report `bridge.port`.
- **Heartbeats (2.3):** `keepAliveMs` is also the hub's heartbeat to peers (a peer drops a hub silent for 2 periods, never under 2 s) and to the worker (it reconnects after 2.25 periods, never under 2 s). `test/integration/heartbeat.test.ts` has a frozen hub (pairs, then never pings) and a raw peer (`pong: false` for a frozen session; `ws._socket.pause()` for one that stops reading); `watchdog.test.ts` has a scripted hub that declares a period and pings or not. Assert *when* a drop happened against the period, measured from the event (the welcome, the backlog showing), and make a race land on purpose (e.g. answer only once the hub has pinged) rather than with a fixed delay. A liveness check (a hub tick, a peer's watchdog) that runs more than half its own wait late (a tick: half a period; the watchdog: half of its 2 periods, at least 1 s; the process stalled) skips its verdict, since the ping or pong may wait unread, but at most once in a row: the next late check judges. `stall(ms)` (`test/helpers/bridgeHarness.ts`) blocks the test process (hub and peer alike) to show both. The extension's watchdog follows the same rule (half of its own wait: 2.25 periods, at least 2 s), shown the same way in `watchdog.test.ts`.
- **Ports:** never fixed, and never picked and then freed (another test file or worktree could take it before it is bound again, #23). Listen on port 0 and read the port from the server that keeps listening (`bridge.port`, `wss.address().port`); a server started from `dist/` with port 0 in its config reports its port in `get_version`.
- **Tool contract:** `test/system/__snapshots__/tools.json` holds every tool's description and input schema. When a change to what the AI sees is intended, update it with `npx vitest run test/system -u` and review the diff.
- **Fixtures:** only fictional people, companies and ids (Alex Doe, Sam Roe, contoso.example, `00000000-…` GUIDs). Never real names, tenants or tokens.
